## ADDED Requirements

### Requirement: Device models own create-draft behavior
Each concrete device model SHALL own the shape and defaults of its create draft so common registry fields and type-specific config fields are represented by a single flat draft object with `deps` as the only nested relationship field.

#### Scenario: Default create draft is type specific
- **WHEN** the UI asks a concrete device model for a default create draft
- **THEN** the model returns a flat draft containing the common registry fields and the model's own type-specific fields with safe defaults

#### Scenario: Create draft preserves common fields
- **WHEN** a user changes the device type in a create flow
- **THEN** the shared common fields remain available while the active model resets only its own type-specific fields to defaults

### Requirement: Device models own create payload encoding
Each concrete device model SHALL own creation payload encoding so registry-only fields are excluded and type-specific config fields are serialized by the model that owns them.

#### Scenario: Payload excludes registry-only fields
- **WHEN** a device create draft is submitted
- **THEN** the model encodes a payload that omits registry-only fields such as the draft type identifier and keeps `deps` only when required by the device type

#### Scenario: Type-specific deps are generated by the model
- **WHEN** a device type requires dependency links at creation time
- **THEN** the device model generates those dependency links as part of its own payload building logic

### Requirement: Device models own config validation and normalization
Each concrete device model SHALL own validation, normalization, and encoding for its type-specific config and SHALL not require the dialog layer to interpret the config structure.

#### Scenario: Model validates its own config
- **WHEN** a create form or adapter passes type-specific fields to the model
- **THEN** the model validates and normalizes those fields according to that device type's rules

#### Scenario: Model produces transport-ready config
- **WHEN** a validated draft is encoded for transport or persistence
- **THEN** the model emits the device-specific config shape expected by the registry or runtime adapter

### Requirement: Device model resolution is centralized
The frontend SHALL resolve concrete device models through a dedicated factory keyed by device type so UI code does not switch on device type when constructing drafts or payloads.

#### Scenario: Factory resolves by type
- **WHEN** the UI knows a device type id or type name
- **THEN** it can obtain the corresponding concrete device model instance from a central factory

#### Scenario: UI delegates to the model
- **WHEN** the create dialog needs defaults, validation, or payload building
- **THEN** it delegates those operations to the resolved device model instead of reconstructing device-specific logic inline
