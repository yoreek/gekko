## ADDED Requirements

### Requirement: Typed config update commands use JSON config at the API boundary
The portal API SHALL accept human-readable JSON config objects for typed device `update_config` commands and keep binary config payload encoding inside firmware adapters and registry storage.

#### Scenario: OneWire update accepts JSON config
- **WHEN** a client sends `POST /api/devices/:id/command` for a OneWire bus with `command = "update_config"` and `config` containing `enabled`, `gpio_pin`, and `internal_pullup`
- **THEN** the OneWire API adapter parses the JSON config, validates the fields, encodes the internal OneWire config payload, and applies the registry update through the existing mutation path

#### Scenario: Invalid OneWire config is rejected before mutation
- **WHEN** a OneWire `update_config` command contains a malformed JSON config, nonnumeric `gpio_pin`, out-of-range `gpio_pin`, or invalid field type
- **THEN** the API returns the standard error envelope and does not change the registry record or runtime configuration

#### Scenario: Binary storage remains internal
- **WHEN** a typed config update is accepted through JSON config
- **THEN** the registry still stores the bounded versioned binary `configPayload` generated by the firmware adapter and does not require clients to construct or inspect that binary format

#### Scenario: Generic command envelope is preserved
- **WHEN** a OneWire JSON config update is submitted
- **THEN** the request still uses the existing `POST /api/devices/:id/command` endpoint, `command = "update_config"`, and standard success or error response envelope

### Requirement: OneWire config JSON is consistent across create and update
The portal API SHALL use the same OneWire config JSON field names and validation semantics for create and update flows.

#### Scenario: Create and update use the same field names
- **WHEN** a client creates or updates a OneWire bus
- **THEN** both flows use `config.enabled`, `config.gpio_pin`, and `config.internal_pullup` as the external JSON field names

#### Scenario: Update serializes back to the same JSON shape
- **WHEN** the API returns the updated OneWire device snapshot after a JSON config update
- **THEN** the snapshot `config` object contains the same external field names and values that clients use for create and update requests
